1. Resumen ejecutivo

VetCare 24 es una clínica y hospital veterinario con atención 24/7. A partir del BRD, las 15 historias de usuario con Gherkin, el BPMN y el diseño DDD elaborados en las unidades 2 y 3, se construyó una API REST en Python (FastAPI) con arquitectura limpia y Domain Model (ADR-001). Las seis reglas de negocio del BRD (RN-01…RN-06) viven en el dominio como objetos que se protegen solos; se implementaron los patrones Specification (AND/OR/NOT), State Machine y Domain Events, persistencia relacional (SQLite/PostgreSQL), contrato OpenAPI/Swagger, pruebas unitarias y de integración, contenedores Docker y CI/CD en GitHub Actions.

2. Análisis del negocio (BRD)

Fuente: BRD del equipo (U2), refinado en docs/BRD.md; los originales en PDF están en docs/analisis/originales/.

2.1 Contexto y problema

Modelo operativo. VetCare 24 es una clínica y centro hospitalario veterinario con atención ininterrumpida (24/7): consultas generales y de especialidad, medicina preventiva, cirugía, laboratorio y hospitalización. Opera con cuenta familiar: un tutor puede tener varias mascotas y cada animal necesita un expediente individual, trazable e independiente.

Problema (AS-IS). Registros físicos y digitales fragmentados: expedientes duplicados; consulta lenta de antecedentes y alergias en urgencias; calendarios de vacunación sin recordatorios; agenda con duraciones estáticas y sin carril de emergencia.

Visión (TO-BE). Plataforma centralizada con expediente unificado tutor–mascotas, agenda por servicio, admisión inmediata de emergencias, notas inmutables con enmiendas auditadas y motor de recordatorios de vacunación.

7. Arquitectura

7.1 Decisión: Domain Model (ADR-001)

Se comparó Transaction Script, Table Module y Domain Model. Se eligió Domain Model (DDD) porque las reglas RN-01…RN-06 son invariantes entrelazadas con ciclo de vida de estados: en un modelo rico el agregado las hace cumplir y se prueban sin base de datos ni servidor web.

Figura 2. Capas y regla de dependencia (api → application → domain ← infrastructure)

7.2 Agregados y patrones

Agregado (raíz)Invariantes
Pacientemicrochip único; alergias sin duplicar; transferencia conserva historial
Consulta (SOAP, enmiendas, receta, estudios)nota firmada inmutable; urgencia sin trámites; resultados de laboratorio se anexan sin editar la nota
Hospitalizacion + Jaulalecturas cada 4 h (2 h en crítico); alta cruzada
RegistroVacunalote y marca obligatorios; refuerzo 21/28/365 días
Citaduración por servicio (15/30/45/90–120 min), sala sin solapes, cancelación tardía < 4 h
OrdenServicio (paquete de datos)puede_procesarse, beneficio de referencia, máquina de estados

Los agregados se referencian solo por identificador (paciente_id, tutor_id), de modo que cada transacción modifica un único agregado.

  • Specification con &, |, ~ y reasons(); p. ej. puede_procesarse = TutorActivo & OrdenConLineas & OrdenAutorizada y beneficio = Preferente & TotalMínimo & ~Promoción.
  • State Machine por tabla (estado × acción → estado) para órdenes, hospitalización y citas; una transición inválida produce InvalidStateTransition (HTTP 409).
  • Domain Events publicados después del commit (ADR-006); suscriptor activo: alerta al médico al recibir un resultado de laboratorio.
  • Repository + Unit of Work; Service Layer delgada (solo orquesta).

12. Diferencias, supuestos y limitaciones

  • Autenticación: X-Rol es solo demostrativo; en producción se sustituye por JWT/OIDC en un único punto (security.requiere).
  • Notificaciones (WhatsApp/correo) simuladas; el mensaje de recordatorio no incluye enlace para confirmar o reagendar (requiere cliente web).
  • Laboratorio: se registra metadato y huella SHA-256 del archivo, no el binario.
  • Rangos de signos vitales (temperatura 37.5–39.5 °C, FC 60–180, FR 10–40) y el esquema de refuerzo por edad son supuestos técnicos pendientes de validación clínica con el Director Médico.
  • US13: el Gherkin menciona «consulta cerrada hace más de 24 h»; el BRD/ADR no fija plazo, por lo que se permite la enmienda en cualquier momento posterior a la firma.
  • Fuera de alcance: consentimiento informado, lista de espera de cancelaciones, pago en línea de estudios externos, inventario de biológicos, interfaz gráfica y alertas sonoras.
  • KPIs de negocio (duplicados < 1 %, +40 % de retorno, código rojo < 15 s) son métricas de operación en producción; el sistema provee los datos pero no pueden demostrarse con datos ficticios.

13. Conclusiones

El Domain Model resultó adecuado: las reglas más delicadas (alergias, inmutabilidad, alta cruzada) quedaron concentradas en pocos métodos de dominio, probados al 100 % sin infraestructura, y la capa de aplicación se mantuvo como orquestadora. Specification y State Machine hicieron que las reglas del paquete de datos fueran explicables (cada rechazo nombra la regla incumplida) y verificables con un oráculo independiente. Probar sobre PostgreSQL real, y no solo SQLite, evitó un fallo de despliegue. La trazabilidad verificada por pruebas reduce el riesgo de documentación desalineada con el código.

Trabajo futuro: autenticación real; adaptador de mensajería; almacenamiento de archivos; consentimiento informado y lista de espera; validación clínica de rangos; cliente web/tablet responsivo (RNF-04); observabilidad.
